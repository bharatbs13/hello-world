# CR-022 — Benchmark Runtime Framework

## Status
**Approved** | Architecture-Frozen Baseline v0.2.1

## Inherited From
CR-013 Benchmark Matrix

## Objective
Provide runtime execution architecture for benchmark execution.

## Owns
- benchmark runtime
- benchmark execution lifecycle
- benchmark adapter registry
- benchmark runtime metadata

## Does Not Own
- benchmark planning (CR-013)
- benchmark configuration (CR-021)
- execution identity (CR-016)
- execution profile governance (CR-025)
- aggregation (CR-015)
- diagnostics (CR-017)

## Inputs
- benchmark execution plan
- execution profile metadata

## Key Requirements

| ID | Requirement | Rule |
|----|-------------|------|
| R1 | Adapter resolution | Benchmark runtime shall resolve benchmark execution through adapters |
| R2 | Solution support | Benchmark runtime shall support solution-specific benchmark implementations |
| R3 | Planning independence | Benchmark runtime shall remain independent of benchmark planning |
| R4 | Lifecycle isolation | Each benchmark execution shall have a defined lifecycle with explicit states |
| R5 | Adapter contract | All benchmark adapters shall conform to a common adapter contract |
| R6 | Deterministic resolution | Identical benchmark cases and configuration shall produce deterministic adapter resolution and lifecycle behavior |
| R7 | Independent concepts | Lifecycle state and execution outcome shall be independent concepts |
| R8 | Outcome required | Completed benchmark executions shall possess an execution outcome |
| R9 | Metric variance | Execution metrics may vary due to runtime conditions |
| R10 | Model-aware resolution | Benchmark runtime shall consume benchmark model metadata during adapter resolution |
| R11 | Execution profile awareness | Benchmark runtime shall consume execution profile metadata provided by benchmark planning |
| R12 | Execution profile independence | Benchmark runtime shall not perform execution profile eligibility determination |

## Execution Lifecycle

### Lifecycle States

```

PENDING
↓
RUNNING
├── COMPLETED
└── ABORTED

```

| State | Description |
|-------|-------------|
| PENDING | Benchmark queued, not yet started |
| RUNNING | Benchmark actively executing |
| COMPLETED | Benchmark finished execution normally |
| ABORTED | Execution terminated before normal completion |

### Execution Outcomes

```

PASSED
FAILED

```

| Outcome | Description |
|---------|-------------|
| PASSED | All thresholds met |
| FAILED | One or more thresholds not met |

### State + Outcome Combinations

| Lifecycle State | Execution Outcome | Meaning |
|-----------------|-------------------|---------|
| PENDING | — | Awaiting execution |
| RUNNING | — | In progress |
| COMPLETED | PASSED | Successful completion |
| COMPLETED | FAILED | Completed with failures |
| ABORTED | — | Terminated before completion |

## Resolution Flow

```

Benchmark execution plan
↓
Execution profile context
↓
Solution identifier
↓
Benchmark model identifier
↓
Adapter registry resolution
↓
Adapter instantiation
↓
Benchmark execution

```

The runtime consumes the execution plan. It does not perform solution detection, benchmark type detection, benchmark model detection, or execution profile eligibility determination. Those are owned by CR-013 (planning), CR-021 (configuration), and CR-025 (execution profile governance).

## Explicitly Forbidden

- `if solution == ... elif solution == ...` inside runtime orchestration
- `if benchmark_model == ... elif benchmark_model == ...` inside runtime orchestration
- Direct coupling between benchmark runtime and benchmark planning
- Hardcoded solution-specific logic in the runtime engine
- Runtime modification of benchmark selection
- Runtime performing solution detection (owned by planning)
- Runtime performing benchmark model detection (owned by planning)
- Runtime performing execution profile eligibility determination (owned by CR-025)
- Runtime overriding execution profile filtering decisions

## Outputs

- **benchmark execution results** — per-execution outcome with state, metrics, and timing
- **benchmark runtime metadata:**
    ```
    benchmark runtime metadata:
      execution_id:        EXEC-001
      benchmark_case:      BENC-001
      solution:            core_runtime
      benchmark_model:     tier_load
      profile:             baseline
      execution_profile:   real_db
      adapter_used:        core_runtime.tier_load_adapter
      resolution_time_ms:  12
      execution_time_ms:   45200
      lifecycle_state:     COMPLETED
      execution_outcome:   PASSED
      state_transitions:
        - PENDING → RUNNING (t=0ms)
        - RUNNING → COMPLETED (t=45200ms)
    ```

## Acceptance Criteria

| ID | Criteria |
|----|----------|
| AC1 | Benchmark runtime resolves correct adapter based on execution plan |
| AC2 | Same execution plan produces deterministic adapter resolution |
| AC3 | Adding a new solution adapter does not require runtime engine modification |
| AC4 | COMPLETED benchmark with failures has outcome FAILED |
| AC5 | ABORTED benchmark terminates before reaching COMPLETED state |
| AC6 | Runtime operates independently of benchmark planning logic |
| AC7 | Runtime metadata captures lifecycle state and execution outcome separately |
| AC8 | Execution metrics (timing, resource usage) may vary between runs |
| AC9 | Adapter resolution consumes benchmark model metadata |
| AC10 | Runtime consumes execution profile metadata |
| AC11 | Runtime does not perform execution profile eligibility determination |
| AC12 | Runtime metadata records execution profile context |

## Architecture Note — Domain, Solution & Execution Profile Awareness

Benchmark runtime executes within the enabled domain, solution, and execution-profile scope provided by CR-021, CR-025, and CR-013. The runtime does not own domain selection, solution selection, or execution profile eligibility determination, but acknowledges that execution occurs within a specific domain partition, solution, and execution profile context.
