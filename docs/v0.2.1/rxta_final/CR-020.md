# CR-020 — Suite Registry & Coverage Selection Framework

## Target Version

v0.2.1

## Status

Draft Final

## Objective

Provide reusable test grouping and deterministic execution selection within RXTA. The framework defines suite registration, suite membership, suite discovery, suite hierarchy, suite-to-solution mappings, coverage-tier mappings, and test selection. Suites provide a reusable mechanism for organizing validation coverage while remaining independent of execution identity, execution planning, topology, infrastructure, domain, and solution concerns.

## Scope

### Owns

- suite definitions
- suite registry
- suite discovery
- suite membership
- parent-child suite relationships
- suite selection
- suite union rules
- suite deduplication rules
- suite mapping metadata consumption
- coverage-tier resolution

### Does Not Own

- execution identity
- execution planning
- execution matrix generation
- topology planning
- infrastructure selection
- report aggregation
- diagnostic analysis
- test execution
- execution result persistence
- domain ownership
- solution ownership
- suite mapping definition

## Inputs

- suite definitions
- suite membership metadata
- suite mapping metadata
- selected suites
- registered test cases
- coverage tier selection
- validation type selection

## Outputs

- selected test cases
- deduplicated test case set
- suite membership metadata
- coverage-tier selection metadata

## Requirements

### R1.

RXTA shall maintain a registry of suite definitions.

### R2.

RXTA shall support suite discovery from the suite registry.

### R2a.

RXTA shall support coverage-tier-driven test selection.

### R2b.

Coverage tiers may be mapped to one or more suites.

### R2c.

Coverage-tier selection shall resolve to suite selection prior to test selection.

### R3.

Suites shall select test cases only.

### R4.

A test case may belong to one or more suites.

### R5.

A suite may contain one or more test cases.

### R6.

Selected suites shall be unioned before execution planning.

### R7.

Duplicate test cases shall be removed prior to execution planning.

### R8.

Suite selection shall be deterministic.

### R9.

Identical suite selections shall produce identical selected test case sets.

### R10.

Suite membership shall be metadata and shall not participate in execution identity generation.

### R11.

Suite definitions shall not encode domain information.

### R12.

Suite definitions shall not encode solution information.

### R12a.

Suite selection may consume domain and solution binding metadata produced by suite mapping configuration.

### R13.

Suites shall not encode topology information.

### R14.

Suites shall not encode infrastructure information.

### R15.

Suites shall not encode execution dimensions.

### R16.

RXTA shall support selection of multiple suites within a single request.

### R17.

Multiple selected suites shall be resolved through union followed by deduplication.

### R18.

RXTA shall support selection of all eligible coverage within the selected scope.

### R19.

All eligible coverage shall be resolved through union followed by deduplication.

### R20.

Parent-child suite relationships shall be explicitly defined within the suite registry.

### R21.

A child suite shall be a subset of its parent suite.

### R22.

Suite selection shall not alter execution identity behavior defined by CR-016.

### R23.

RXTA shall support suite selection through the `--suites` command argument.

### R23a.

RXTA shall support coverage tier selection through the `--coverage-tier` command argument.

### R23b.

Coverage tier aliases may be mapped to internal suite names.

### R23c.

The CLI value `full` may map to the internal suite `feature`.

### R24.

RXTA shall support selection of all eligible coverage through the `--all` command argument.

### R25.

Suite selection shall support suite-to-solution bindings defined through suite mapping metadata.

## Architecture Notes

### Default Functional Suites

| Suite | Purpose | Size |
|---------|---------|---------|
| sanity | Verify environment, deployment, configuration, and framework readiness | Very Small |
| smoke | Verify critical end-to-end functionality | Small |
| feature | Full PV feature validation | Medium / Large |
| regression | IV inherited behavior validation | Large |

### Suite Hierarchy

```text
sanity ⊂ smoke ⊂ feature
```

Rules:

· sanity is a subset of smoke
· smoke is a subset of feature

Coverage Tier Model

```text

        ↓
```

Suite Membership Model

Example:

```yaml
test_id: UAT-V021-FUNC-001
suites:
  - sanity
  - smoke
  - feature

test_id: UAT-V021-FUNC-005
suites:
  - smoke
  - feature

test_id: UAT-V021-FUNC-020
suites:
  - feature
```

Suite Mapping Model

Suite definitions are independent of domain and solution. Suite mappings provide domain and solution bindings:

```yaml
suite_bindings:
  smoke:
    solutions:
      - core_runtime
  feature:
    solutions:
      - core_runtime
      - migration
```

Suite mapping metadata is consumed by CR-020. Suite mapping definition is owned externally.

Selection Model

Single suite:

```text
suite
    ↓
test cases
```

Multiple suites:

```text
suite A
      \
       → union → deduplicate → selected test cases
      /
suite B
```

All eligible coverage:

```text
enabled domain partitions
        ↓
enabled solutions
        ↓
all eligible coverage
        ↓
union
        ↓
deduplicate
        ↓
selected test cases
```

Suite selection operates within the enabled domain and solution scope provided by catalog governance.

CLI Selection Model

```text
rxta test --coverage-tier sanity
rxta test --coverage-tier smoke
rxta test --coverage-tier full
rxta test --suites sanity
rxta test --suites smoke
rxta test --suites feature
rxta test --suites regression
rxta test --suites sanity,smoke
rxta test --all
```

--all selects all eligible coverage within the enabled domain and solution scope.

Execution Identity Relationship

Suites are selection metadata.

Suites do not create execution identity.

Suite membership may be present in execution context as metadata, but shall not participate in execution_id generation as defined by CR-016.

Relationship to CR-018


CR-018 determines which historical coverage is eligible.

CR-020 determines which eligible coverage is selected.

Future Compatibility

The suite framework shall support future suite definitions without requiring redesign.

Examples include:

· frontend validation suites
· mobile validation suites
· migration validation suites
· backup validation suites
· disaster recovery validation suites

Future suite definitions shall not encode domain or solution.

Domain and solution filtering remain catalog responsibilities and are outside the scope of CR-020.

Future suite definitions shall also remain independent of:

· topology
· connector
· worker_cores
· parallel_mode
· vm_profile

Future suite-to-solution mappings may be introduced through external suite mapping metadata.

Selecting a single suite returns all test cases assigned to that suite.

AC2.

AC3.

Duplicate test cases are removed before execution planning.

AC4.

Identical suite selections produce identical selected test case sets.

AC5.

A test case may belong to multiple suites.

AC6.

The sanity suite is a subset of the smoke suite.

The smoke suite is a subset of the feature suite.

AC8.

Suite membership does not affect execution identity generation.

AC9.

--suites smoke selects the smoke suite.

AC10.

--suites smoke,feature selects the union of smoke and feature.

AC11.

--all selects all eligible coverage within enabled domain and solution scope.

AC12.

Suite selection consumes suite mapping metadata for solution bindings.

AC13.

Coverage tier selection resolves to deterministic suite selection.

AC14.

Coverage tier full resolves to feature coverage.

AC15.

Coverage tier smoke resolves to smoke coverage.

AC16.

Coverage tier sanity resolves to sanity coverage.

AC17.

Coverage tier selection produces selected test cases.
