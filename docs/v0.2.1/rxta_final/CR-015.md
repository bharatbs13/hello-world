# CR-015 — Validation Aggregation Framework

## Target Version

v0.2.1

## Status

Draft Final

## Objective

Generate release evidence and validation reports for RXTA. The framework aggregates validation outcomes, execution metadata, benchmark outcomes, traceability information, and execution statistics into standardized reporting views. Aggregation supports complete, partial, incremental, resumed, and best-effort run aggregation while remaining independent of execution planning, execution identity generation, topology planning, and runtime execution.

### R22.

Aggregation shall remain valid when aggregation dimensions are absent. Missing aggregation dimensions shall be represented through configured null buckets.

### R23.

Aggregation shall support execution metadata produced by CR-016.

### R24.

Aggregation shall support functional validation outputs produced by CR-012.

### R25.

Aggregation shall support benchmark validation outputs produced by CR-013.

### R26.

Aggregation views shall be deterministic for identical inputs.

Summary statistics shall be deterministic for identical inputs.

### R28.

Aggregation shall support the current enabled domain partition set. Current PV v0.2.1 contains one enabled domain partition.

### R29.

Aggregation shall support the current enabled solution set. Current PV v0.2.1 contains one enabled solution.

### R30.

Aggregation shall not require redesign when new aggregation dimensions are introduced.

### R31.

Aggregation shall be best-effort within a run_id.

### R32.

Failure to aggregate one execution shall not prevent aggregation of other executions within the same run.

### R33.

Missing, corrupted, incomplete, or unavailable execution artifacts shall be reported as aggregation anomalies.

### R34.

Aggregation shall produce partial reports when one or more executions cannot be aggregated.

### R35.

Aggregation shall operate at run_id scope.

### R36.

Aggregation shall aggregate execution records contained within a single run_id.

### R37.

Aggregation shall consume failure classification when available.

### R38.

Aggregation shall not generate failure classification.

### R39.

Aggregation shall support configurable aggregation dimensions through aggregation configuration.

### R40.

Aggregation group_by shall support a single dimension or an ordered list of dimensions.

### R41.

Functional and regression validation reporting shall support aggregation views.

### R42.

Load and performance validation reporting shall preserve benchmark detail records by default.

### R43.

Load and performance validation reporting shall not require metric aggregation.

### R44.

Aggregation shall support domain-partition metadata generated by enabled domain partitions.

### R45.

Each aggregation operation shall possess exactly one aggregation_id.

### R46.

Aggregation metadata shall record the source run_id.

### R47.

Aggregation outputs shall be traceable to aggregation_id.

### R48.

Aggregation shall preserve benchmark identity metadata when provided by benchmark results.

### Failure Traceability

Failure traceability records contain:

```text
execution_id
test_case_id
failure_classification
artifact_references
```

Reporting Rules

```text
execution_id
    ↓
reporting unit

test_case_id
    ↓
traceability unit

suite
    ↓
aggregation metadata
```

Aggregation Outcomes

```text
COMPLETE
PARTIAL
FAILED
```

Outcome Description
COMPLETE All eligible executions aggregated successfully
PARTIAL One or more executions could not be aggregated
FAILED Aggregation could not produce reports

Load and Performance Report Identity

Load and performance reports may additionally preserve benchmark identity metadata including benchmark_case, solution, topology_signature, and profile.

Aggregation Identity Model

```text
run_id
    ↓
aggregation_id
    ↓
aggregation views
    ↓
reports
```

Each aggregation operation receives a unique aggregation_id. Aggregation outputs are traceable to aggregation_id. Aggregation metadata records the source run_id.

Aggregation Scope Model

```text
run_id
    ↓
executions
    ↓
aggregation
    ↓
standard reports
```

Aggregation Relationship

```text
CR-012
    ↓
functional results

CR-013
    ↓
benchmark results

CR-016
    ↓
execution metadata

CR-015
    ↓
aggregation
    ↓
reports
    ↓
release evidence
```

Incremental Aggregation Model

```text
execution completed
        ↓
aggregation update
        ↓
summary update
        ↓
report update
```

Aggregation may occur before all executions complete.

Aggregation remains valid for:

· partial runs
· complete runs
· resumed runs
· incrementally completed runs

Best-Effort Aggregation Model

```text
execution A     → aggregated
execution B     → aggregated
execution C     → missing
execution D     → aggregated

result:
partial report generated
aggregation anomaly recorded
```

Aggregation shall not fail solely because one execution cannot be aggregated.

Aggregation Anomaly States

· AGGREGATED
· MISSING
· CORRUPTED
· INCOMPLETE
· UNAVAILABLE

Null Bucket Representation

When an aggregation dimension is absent from execution metadata, aggregation shall represent the missing dimension through a configured null bucket value.

Example null bucket values:

```text
NO_TOPOLOGY
NO_CONNECTOR
NO_DOMAIN
```

Aggregation Dimension Model

Aggregation dimensions are metadata-driven.

Examples:

```text
domain
solution
depth_id
topology_signature
connector_type
worker_cores
parallel_mode
vm_profile
```

Aggregation shall not assume the existence of any specific dimension.

Dimensions may be:

```text
present
absent
```

without invalidating aggregation.

Configurable group_by

Aggregation configuration may specify:

```yaml
group_by:
  - solution
  - topology_signature
```

or:

```yaml
group_by: solution
```

Aggregation shall support a single grouping dimension or an ordered list of grouping dimensions.

Failure Classification Boundary

Failure classification may originate from:

· execution results
· diagnostic analysis
· future diagnostic frameworks

CR-015 consumes failure classification when available.

CR-015 does not generate failure classification.

Benchmark Identity Preservation

When benchmark results provide benchmark identity metadata, aggregation shall preserve:

```text
benchmark_case
solution
topology_signature
profile
```

in load and performance reports.

Current Cardinality

For PV v0.2.1:

```text
domain partition set: one enabled domain partition (backend)
solution set: one enabled solution (core_runtime)
```

Future Compatibility

The aggregation framework shall support future aggregation dimensions without redesign.

Examples include:

· suite
· domain
· solution
· depth
· topology
· connector
· worker_cores
· parallel_mode
· vm_profile

Future validation categories may also be introduced while preserving the aggregation architecture.

Examples:

· migration validation
· backup validation
· restore validation
· disaster recovery validation
