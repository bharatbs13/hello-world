# CR-024 — Catalog & Version Governance Framework

## Target Version

v0.2.1

## Status
**Approved** | Architecture-Frozen Baseline v0.2.1

## Objective
Provide foundational governance for UAT catalog structure, catalog validation, version catalog management, and version status lifecycle. The framework owns the authoritative catalog schema and version metadata that drive execution planning, suite selection, and regression eligibility across all RXTA subsystems.

## Owns
- UAT catalog schema
- catalog validation
- version catalog
- version status lifecycle
- version status transitions
- catalog metadata authority

## Does Not Own
- domain partition governance
- domain partition enablement
- regression governance
- regression.yml
- execution planning (CR-012, CR-013)
- execution identity (CR-016)
- suite definitions (CR-020)
- suite selection (CR-020)
- topology planning (CR-014)
- benchmark configuration (CR-021)
- runtime execution (CR-022)
- aggregation (CR-015)
- diagnostic analysis (CR-017)

## Inputs
- UAT catalog files
- catalog schema definition
- version metadata
- version status records

## Outputs
- validated UAT catalog
- version status records
- version lifecycle metadata
- catalog metadata consumable by CR-012, CR-013, CR-014, CR-020, CR-025

## Key Requirements

### Catalog Schema

| ID | Requirement | Rule |
|----|-------------|------|
| R1 | Catalog authority | UAT catalog shall be the authoritative source for test case definitions |
| R2 | Schema-driven | UAT catalog shall conform to a defined catalog schema |
| R3 | Catalog validation | UAT catalog shall be validatable for structural correctness |
| R4 | Metadata-driven membership | Test case domain, solution, suite, execution_profile, and topology membership shall be declared through metadata |
| R5 | Schema evolution | Catalog schema shall support evolution without breaking existing catalog files |

### Version Lifecycle

| ID | Requirement | Rule |
|----|-------------|------|
| R6 | Version catalog | RXTA shall maintain a version catalog with status metadata |
| R7 | Version states | Version status shall support PROPOSED, IN_PROGRESS, REJECTED, ACCEPTED, and SUPERSEDED states |
| R8 | Status authority | Version status shall be authoritative for execution scope |
| R9 | Status transitions | Version status transitions shall be governed by the version catalog |
| R10 | Version discovery | Version status and metadata shall be discoverable from the version catalog |
| R11 | Deterministic status | Version status resolution shall be deterministic for identical catalog inputs |

## Architecture Notes

### Catalog as Authoritative Source

Catalog metadata is the authoritative source for:

- test case identity
- domain membership
- solution membership
- suite membership
- execution profile eligibility
- topology participation

No subsystem shall independently determine domain, solution, or suite membership outside catalog metadata.

### Catalog Schema Model

```yaml
# catalog schema example
schema_version: 1.0

test_case:
  test_id: UAT-V022-FUNC-001
  domain: backend
  solution: core_runtime
  execution_profiles:
    - real_db
  suites:
    - sanity
    - smoke
    - feature
  topology_participation: true
```

Catalog schema versions may be recorded through schema_version metadata. Schema evolution shall preserve backward compatibility for valid previous schema versions.

Version Status Model

```text
PROPOSED
    ↓
IN_PROGRESS
    ├── REJECTED
    └── ACCEPTED
            ↓
        SUPERSEDED
```

State Description
PROPOSED Version planned, not yet in development
IN_PROGRESS Version under active development
REJECTED Version rejected, will not be delivered
ACCEPTED Version accepted and validated
SUPERSEDED Version replaced by a newer accepted version

Version Catalog Model

```yaml
# version catalog example
versions:
  - version: v0.2.0
    status: ACCEPTED
  - version: v0.2.1
    status: IN_PROGRESS
  - version: v0.2.2
    status: PROPOSED
```
