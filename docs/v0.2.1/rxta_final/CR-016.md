# CR-016 — Execution Identity Framework

## Target Version
v0.2.1

## Status
Draft

## Objective

Provide unique run and execution traceability for RXTA. The framework establishes execution as the atomic unit of validation, defines execution identity, execution context, execution workspaces, configuration freezing, execution result persistence, lifecycle management, and audit preservation. The framework ensures reproducible execution, deterministic traceability, and future extensibility without requiring redesign when new execution dimensions are introduced.

## Scope

### Owns

- run_id
- execution_id
- execution context
- execution workspace
- execution lifecycle
- configuration resolution
- configuration freeze
- execution traceability
- execution result persistence
- execution-level cleanup
- audit preservation

### Does Not Own

- suite selection
- topology planning
- infrastructure selection
- execution matrix generation
- report aggregation
- diagnostic analysis
- test execution logic

## Inputs

- test_case_id
- phase
- execution dimensions
- execution configuration
- optional run_id

## Outputs

- run_id
- execution_id
- execution_context.json
- effective_config.json
- execution_result.json
- execution workspace

## Requirements

### R1.

RXTA shall generate a new run_id when no run_id is supplied.

### R2.

RXTA shall append execution results to an existing run when a valid run_id is supplied.

### R3.

RXTA shall fail execution when a supplied run_id does not exist.

### R4.

Execution shall be the atomic execution unit within RXTA.

### R5.

Every execution shall possess exactly one execution_id.

### R6.

Every execution shall possess exactly one immutable execution context.

### R7.

Execution context shall be persisted before execution begins.

### R8.

Execution context shall be stored as execution_context.json.

### R9.

Execution context shall contain all mandatory execution dimensions and any applicable optional execution dimensions.

### R10.

Execution ID shall be derived from execution context.

### R11.

Execution ID generation shall be deterministic for identical execution contexts.

### R12.

Execution IDs shall be unique within a run.

### R13.

The same execution ID may appear in different runs.

### R14.

Duplicate execution contexts within a run shall not execute more than once.

### R15.

Every execution shall possess an isolated execution workspace.

### R16.

Execution workspaces shall prevent collisions between artifacts, logs, reports, and state generated by different executions.

### R17.

Configuration resolution shall complete before execution begins.

### R18.

Resolved configuration shall be persisted as effective_config.json.

### R19.

Effective configuration shall remain immutable for the duration of execution.

### R20.

Execution artifacts shall be traceable to both run_id and execution_id.

### R21.

A single test execution shall be represented as a run containing one execution.

### R22.

Suite execution shall be represented as a run containing one or more executions.

### R23.

Execution identity shall remain independent of execution selection method.

### R24.

Execution cleanup may occur at execution granularity.

### R25.

Cleanup shall preserve audit-required artifacts.

### R26.

Execution outcome shall be persisted as execution_result.json.

## Architecture Notes

- Execution is the atomic execution and traceability unit.
- Run is a container of executions.
- Execution context is an immutable snapshot captured before execution begins.
- Execution identity is derived from execution context.
- Configuration is resolved and frozen before execution begins.
- Execution workspaces are isolated from one another.
- Execution selection mechanisms do not alter execution identity.
- Execution traceability is maintained through run_id and execution_id.

### Mandatory Execution Context Dimensions

- test_case_id
- phase

### Optional Execution Context Dimensions

- depth_id
- topology_signature
- suite_membership
- domain
- solution
- worker_cores
- parallel_mode
- vm_profile
- connector

### Execution ID Participation

#### Mandatory Participants

- test_case_id
- phase

#### Optional Participants (If Present)

- depth_id
- topology_signature
- connector
- domain
- solution
- worker_cores
- parallel_mode
- vm_profile

#### Excluded Participants

- run_id
- suite_membership

### Suite Membership Rule

- suite_membership may be recorded within execution context.
- suite_membership shall not participate in execution_id generation.
- Suite membership is execution metadata and not execution identity.

### Run Workspace Rule

A run shall be represented by a dedicated run workspace.

Execution workspaces shall exist only within a run workspace.

### Execution Workspace Model

```text
run_id/
    executions/
        execution_id/
            execution_context.json
            effective_config.json
            execution_result.json
            logs/
            artifacts/
            reports/
            state/
```

### Configuration Resolution Model

```text
global configuration
        ↓
suite configuration
        ↓
execution overrides
        ↓
execution context
        ↓
effective_config.json
```

## Future Compatibility

The framework shall support future execution dimensions without requiring redesign of execution identity architecture.

Examples include:

- domain
- solution
- topology
- connector
- worker_cores
- parallel_mode
- vm_profile
- execution environment
- deployment profile

New dimensions may be introduced as optional execution context fields.

## Acceptance Criteria

### AC1.

Executing a single test without a supplied run_id creates exactly one run_id and one execution_id.

### AC2.

Executing multiple tests under the same run_id produces multiple execution_ids within the same run.

### AC3.

Supplying a non-existent run_id causes execution to fail.

### AC4.

Duplicate execution contexts within a run are not executed more than once.

### AC5.

Execution context is persisted before execution begins.

### AC6.

Effective configuration is persisted before execution begins.

### AC7.

Execution workspaces remain isolated from one another.

### AC8.

Cleanup preserves audit-required artifacts.

### AC9.

Execution identity remains unchanged regardless of whether execution originated from a single test, suite selection, multiple suites, or full execution.

### AC10.

Identical execution contexts produce identical execution IDs.

### AC11.

Execution contexts that differ by at least one execution ID participating dimension produce different execution IDs.
