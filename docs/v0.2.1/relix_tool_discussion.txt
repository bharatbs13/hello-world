CR-006 — Automate relix-tools Deployment to relix-vm
Status: Planned for v0.2.1
Problem: Tests execute on relix-vm but relix-tools (test files, modules, automation/) is only on relix-tools-vm. Current workaround is manual SCP.
Requirement: relix-deploy deploy must automatically copy relix-tools to relix-vm and install test dependencies in the venv.
Updated deploy flow: git clone relix → checkout ref → create venv → pip install relix → scp relix-tools to relix-vm → pip install pytest + deps in venv.
YAML addition: sync_tools_to_runtime: true, install_test_deps: true under lifecycle.deploy.
Non-goals: relix-tools is not pip-installed as a package. relix-tools repo is not cloned on relix-vm (SCP copy only).

CR-007 — Command-Aware Prompt Resolution
Status: Planned for v0.2.1
Problem: All PROMPT placeholders and GitHub token resolve upfront regardless of command. Delete/stop/start prompt for DB host and GitHub token unnecessarily.
Requirement: Prompt resolution must be command-scoped. Deploy needs VM IPs, username, GitHub token. Test needs VM IPs, username, DB host. Start/stop/delete need VM IPs, username only.



CR-008 — Pytest Report Integration for Combined Summary
Status: Planned for v0.2.1
Problem: Test suites run via pytest but output goes to stdout only. No report.json written to report directory. Combined summary tables show empty because no discoverable report files exist.
Requirement: Test commands must generate structured output that combined_summary.py can discover and aggregate.
Approach: Add --junitxml to pytest commands in YAML. Update combined_summary.py to discover and parse both report.json and report.xml (junit). Populate Table 1 from junit XML when report.json is absent.
Non-goal: Custom pytest plugin. Keep it simple — junit XML is standard pytest output.

Yes — for feature/regression, fixed DB per connector is better.
 
Because feature/regression should answer:
Does this connector work correctly?
Did this connector regress?
So each DB connector should have explicit tests:
feature/postgres/
feature/mysql/
feature/sqlserver/
feature/oracle/
or:
feature/
  test_postgres_connector.py
  test_mysql_connector.py
  test_sqlserver_connector.py
The DB type should be intentional, not randomly selected.
Correct split
Test type	DB selection
Feature	Fixed / explicit DB connector
Regression	Fixed / explicit DB connector
Load same VM	Depth D / random or full-set allowed
Performance same VM	Depth D / random or full-set allowed
Cross-VM scaling	Fixed DB only
Why
Feature/regression need deterministic coverage:
Postgres connector PASS
MySQL connector PASS
Oracle connector PASS
Random DB selection could miss one connector.
Load/performance can use D because they study behavior across infrastructure.
CR-005 v0.2.1 rule
Add this:
Feature and regression suites MUST use explicit infrastructure selection.

Load and performance suites MAY use fixed, random, or full-set infrastructure selection depending on benchmark objective.

Cross-VM scalability benchmarking MUST use fixed infrastructure selection.
So yes: hardcode DB type in feature/regression tests or bind each test to an explicit connector profile.
