In fact, that should be the primary acceptance criterion for v0.2.2.
 
A common failure mode is:
1 worker  -> 1000 rows/sec
2 workers -> 850 rows/sec
4 workers -> 600 rows/sec
because of:
Lock contention
Context switching
Thread synchronization
Shared queues
Connection pool bottlenecks
Database contention
Memory pressure
Then “parallelism” is actually making things worse.
 
So v0.2.2 should not be:
Add workers
It should be:
Add workers only when beneficial
I would define the principle as:
FR-070 — Adaptive Parallel Snapshot Execution

Objective:
Utilize available compute resources without reducing throughput.

Acceptance:
Parallel execution MUST NOT materially degrade throughput relative to single-worker execution under equivalent workload conditions.
Then test:
Workers	Throughput
1	baseline
2	compare
4	compare
8	compare
Expected:
2 workers >= 1 worker
4 workers >= 2 workers
Not necessarily linear scaling, but:
No regression
is the first requirement.
 
I would actually make v0.2.2 milestones:
Phase 1
    Add worker framework

Phase 2
    Benchmark scaling

Phase 3
    Auto-select optimal worker count
because many systems find that:
2 workers = best
4 workers = same
8 workers = worse
The goal is not “maximum parallelism”.
 
The goal is:
maximum throughput
minimum latency
minimum resource waste
which may end up being fewer workers than available cores.

For your current roadmap, yes.
Relix v0.2.2 should limit parallelism to the data plane.
Control Plane
    ↓
creates execution plan
starts workflow
tracks status
manages checkpoints
publishes events

Data Plane
    ↓
reads data
transforms data
writes data
reconciles data
Only the data plane should become parallel.
Examples:
✓ Parallel snapshot readers
✓ Parallel batch processors
✓ Parallel writers
✓ Parallel reconciliation workers

✗ Parallel preflight
✗ Parallel workflow orchestration
✗ Parallel state machine management
✗ Parallel deployment lifecycle
Reason:
Control plane work is tiny.
Data plane work is expensive.
Almost all throughput comes from:
Read
Transform
Write
Verify
which are data-plane activities.
 
⸻
 
So I would define v0.2.2 as:
FR-070 Internal Data Plane Parallelism
Scope:
Single Relix instance
Single VM
Multiple data workers
Shared control plane
Architecture:
Control Plane (single)
        │
        ▼
    Work Queue
        │
 ┌──────┼──────┐
 ▼      ▼      ▼
W1     W2     W3
        ...
Then later in DWE:
Control Plane
        │
        ▼
 Distributed Queue
        │
 ┌──────┼──────┐
 ▼      ▼      ▼
VM1    VM2    VM3
That’s the natural progression.
So my answer is:
Relix v0.2.2:
    Internal parallelism = Data Plane only

Control Plane remains single-threaded/single-owner.
That keeps the scope manageable and avoids introducing unnecessary complexity into orchestration logic.

Yes, but it should be minimal integration code, not a redesign.
Ideal model:
Parallelism framework = stable
New data-plane feature = registers a task adapter
So for each new data-plane capability, you add:
partition strategy
worker function
merge/reconcile strategy
safety flags
Example:
snapshot_adapter
migration_adapter
backup_restore_adapter
replay_adapter
Each adapter answers:
Can this task be parallelized?
How should work be split?
How should worker results be merged?
What state/checkpoint rules apply?
So yes, every new data-plane feature needs some code, because each feature has different semantics.
But it should be limited to:
new adapter/plugin
tests
config entry
not changes to the core parallel engine.
Good rule:
Core parallel executor should remain unchanged.
New data-plane functions extend it through adapters.
So:
Code change required?        Yes
Core redesign required?      No
Expected change size?        Small to medium
That is the right architecture.
