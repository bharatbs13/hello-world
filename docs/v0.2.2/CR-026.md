# CR-026 — RXTA-Owned UAT Environment Script Governance

## Status

**Approved for v0.2.2**

---

# Objective

Establish RXTA (`relix-tool`) as the sole owner of all UAT environment lifecycle tooling, ensuring that the Relix runtime repository contains only product code.

RXTA governs the complete lifecycle of UAT infrastructure, including deployment, installation, environment setup, readiness verification, deployment artifact management, and optional storage cleanup.

---

# Scope

RXTA owns the following scripts under:

```text
relix-tool/
└── automation/
    └── deploy/
        └── scripts/
            ├── install_storage.sh
            ├── setup_uat_storage.sh
            ├── verify_storage.sh
            └── cleanup_storage.sh
```

These scripts provision, initialize, verify, and optionally clean UAT storage environments.

The scripts are considered part of the RXTA deployment framework and are not part of the Relix runtime.

---

# Ownership Rules

## RXTA Owns

* UAT environment scripts
* deployment to target environments
* installation
* environment setup
* readiness verification
* deployment logging
* deployment artifact lifecycle
* optional storage cleanup

## Relix Runtime Owns

* runtime code
* application logic
* storage access
* migrations
* runtime configuration
* business functionality

The Relix runtime shall not depend upon RXTA UAT scripts.

---

# Script Governance

## Script Requirements

Scripts shall:

* be versioned with RXTA
* be deterministic
* support repeated execution where practical
* support backend selection
* report unsupported backends as `SKIPPED`
* return non-zero exit codes only for genuine failures
* generate deterministic execution logs
* support readiness verification after installation and setup

Verification shall be read-only and shall never modify backend state.

---

## Installation Requirements

Installation scripts shall execute deterministically without requiring manual user interaction.

Installation shall:

* execute in unattended (non-interactive) mode
* complete successfully or terminate with a deterministic failure
* never pause awaiting console input
* never rely on manual confirmation during automated deployment
* return an appropriate exit status upon completion

Platform-specific mechanisms (for example, non-interactive package manager modes) may be used to satisfy this requirement.

---

## Timeout Governance

Installation, setup, and verification operations shall support configurable execution timeouts.

Operations exceeding the configured timeout shall terminate with `FAILED` and include a timeout diagnostic message.

Timeout values shall be configurable through RXTA deployment policy.

---

## Retry Governance

Deployment tooling may retry recoverable installation and verification failures according to RXTA deployment policy.

Retry behavior shall be deterministic and auditable.

Retry attempts shall be recorded in deployment logs.

---

## Package Manager Behaviour

When installation requires operating-system package management, installation scripts shall:

* invoke the package manager in non-interactive mode
* detect package installation failures
* detect incomplete or pending package configuration
* detect package-manager lock or transaction failures
* terminate cleanly if installation cannot proceed automatically

Installation scripts shall not remain blocked waiting for:

* confirmation prompts
* configuration dialogs
* license acceptance dialogs
* terminal input
* package-manager questions

Any such condition shall be treated as an installation failure.

---

## Installation Verification

Upon completion of installation, verification shall determine whether installation completed successfully.

Verification shall distinguish between:

* installation completed successfully
* installation failed
* installation incomplete
* installation pending manual configuration

Verification diagnostics shall include the reason when installation is not successful.

Example diagnostic messages include:

* package manager returned non-zero exit status
* package installation requires manual configuration
* package manager transaction incomplete
* package manager lock unavailable
* required package not installed

---

## Deployment Logging

Deployment logs shall record:

* deployment identifier
* execution identifier
* host identifier
* deployed RXTA version
* deployed script version
* backend
* executed operation
* execution status
* execution result
* timestamp

Deployment logs shall allow operators to determine whether failure occurred during:

* install
* setup
* verify

without requiring manual inspection of the deployment host.

---

# Verification Contract

Verification validates that a backend is correctly prepared for UAT execution.

Verification shall execute mandatory verification checks:

* installation completion
* service availability
* setup completion

Verification may execute backend-specific optional checks including:

* authentication
* connectivity
* schema validation
* test object availability
* configuration validation

Verification shall execute without requiring manual SSH inspection of the target environment.

---

# Verification Status

Each backend shall report individual verification results.

Verification results are organized by check category:

**Installation**
* `INSTALLED`
* `NOT_INSTALLED`

**Service**
* `SERVICE_READY`
* `SERVICE_NOT_READY`

**Setup**
* `SETUP_READY`
* `SETUP_NOT_READY`

**Execution**
* `PASSED`
* `FAILED`
* `SKIPPED`
* `NOT_APPLICABLE`

`FAILED` and `SKIPPED` shall include a diagnostic reason.

---

# Overall Readiness

Verification shall additionally compute an aggregate readiness state.

Supported readiness states are:

| State             | Meaning                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------- |
| `READY`           | All mandatory verification checks passed.                                                |
| `PARTIALLY_READY` | Mandatory checks passed but one or more optional components were unavailable or skipped. |
| `NOT_READY`       | One or more mandatory verification checks failed.                                        |

Automated UAT execution shall not begin unless the backend aggregate readiness is `READY` or `PARTIALLY_READY` according to RXTA deployment policy.

---

# Verification Output

Verification shall produce:

* human-readable console output
* machine-readable structured output suitable for deployment automation

The structured output shall contain, at minimum:

* backend
* installation status
* service status
* setup status
* overall readiness
* diagnostic message (if applicable)

The machine-readable output shall include a schema version identifier.

Consumers shall ignore unknown fields to preserve forward compatibility.

---

# Deployment Lifecycle

## Deploy

`relix-deploy` may copy UAT scripts to the target environment and execute:

* install
* setup
* verify
* cleanup (only when explicitly requested)

## Verify

Verification confirms backend readiness for UAT.

Verification shall execute automatically when requested and shall not modify backend state.

Verification shall be executable independently of deployment.

## Delete

`relix-deploy delete` removes only deployment artifacts.

Deployment artifacts include only files copied to the target environment.

Examples include:

* deployed UAT scripts
* temporary deployment files
* temporary execution directories

Typical deployment locations include:

```text
/opt/relix-workspace/uat-artifacts
/tmp/relix-uat-*
```

Canonical copies remain inside the RXTA repository.

Database objects shall **not** be removed by default.

---

## Storage Cleanup

Storage cleanup is an explicit operation.

Examples:

```bash
relix-deploy cleanup-storage --backend postgres
```

or

```bash
relix-deploy delete --cleanup-storage
```

Cleanup may include:

* dropping UAT databases
* removing test schemas
* removing test users
* resetting storage state

Storage cleanup shall:

* require explicit invocation
* be auditable
* never execute automatically during deployment deletion

---

# UAT Lifecycle

```text
Deploy
    ↓
Install storage
    ↓
Setup storage
    ↓
Verify readiness
        ├── Human-readable report
        ├── Machine-readable report
        └── Overall readiness
    ↓
Run UAT
    ↓
Delete deployment artifacts

Optional
    ↓
Cleanup storage
```

# Acceptance Criteria

* UAT environment scripts exist under `relix-tool/automation/deploy/scripts`.
* `relix-deploy` can deploy and execute all lifecycle scripts on the target environment.
* The Relix runtime repository contains no UAT infrastructure scripts.
* Setup is safe for repeated execution where practical.
* Unsupported backends report `SKIPPED`.
* Verification is read-only.
* Verification executes without manual SSH inspection.
* Verification produces both human-readable and machine-readable output.
* Verification output includes a schema version identifier.
* Verification output consumers ignore unknown fields.
* Aggregate readiness is reported as `READY`, `PARTIALLY_READY`, or `NOT_READY`.
* Automated UAT execution gates on aggregate readiness according to RXTA deployment policy.
* Deployment logs capture deployment identifier, execution identifier, host identifier, version, backend, operation, status, result, and timestamp.
* `relix-deploy delete` removes only deployment artifacts by default.
* Canonical script copies remain within the RXTA repository.
* Storage cleanup requires explicit user invocation.
* Deployment artifact cleanup and storage cleanup are independently executable.
* Installation executes without requiring manual operator interaction.
* Installation never blocks awaiting package-manager prompts.
* Package-manager prompts are reported as installation failures with diagnostic information.
* Incomplete or pending package configuration is detected during verification.
* Deployment logs clearly distinguish installation failures from setup and verification failures.
* Automated deployment either completes successfully or fails deterministically without hanging.
* Installation, setup, and verification operations support configurable execution timeouts.
* Timeout diagnostics are included when operations exceed configured timeout values.
* Retry behavior, where implemented, is deterministic and auditable.
