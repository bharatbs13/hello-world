# CR-029 — Dynamic Topology Generation & Scheduling Framework

| Property | Value |
|----------|-------|
| **Status** | Approved for inclusion in RXTA v0.2.2 |
| **Type** | Core Requirement (Architecture Enhancement) |

---

# 1. Objective

Provide a topology generation and scheduling framework that automatically derives executable topology signatures from enabled integration endpoints and distributes them across validation workloads to maximize coverage while maintaining deterministic, bounded execution.

---

# 2. Problem Statement

Current topology selection in RXTA is static and manually declared. As integration endpoints expand beyond databases to include warehouses, object stores, streams, queues, REST APIs, and files, the combinatorial growth of valid topology combinations makes manual declaration unsustainable. Furthermore, executing every test against every topology creates unacceptable runtime explosion while providing diminishing validation returns.

Three core problems are addressed:

1. **Discovery** — How are valid topologies identified from enabled endpoints?
2. **Selection** — How many and which topologies should be considered?
3. **Assignment** — Which topology should each test run on to maximize coverage?

---

# 3. Scope

## 3.1 Applicability

CR-029 applies only to data-management validation or integration-endpoint-dependent validation.

It does **not** apply to generic framework features such as:

- License validation
- Authentication
- Governance
- Prompt resolution
- Catalog validation

Generic features skip topology generation (for example, v0.2.2 License UAT).

## 3.2 Out of Scope

- Individual connector implementation details
- Benchmark execution logic
- UAT business logic
- Infrastructure provisioning
- Endpoint deployment orchestration
- Runtime installation
- Runtime availability verification

## 5.2 Solution Topology Templates

Defines how a solution constructs valid topology signatures.

### Template Properties

| Property | Description |
|----------|-------------|
| Arity | Number of endpoints |
| Ordering | Ordered or unordered |
| Slot Definitions | Allowed endpoint categories per slot |

## 5.3 Topology Generator

Generates valid topology candidates.

### Generation Modes

| Mode | Description |
|------|-------------|
| Bounded | Small subset |
| Representative | Diverse sample |
| Exhaustive | Every valid candidate |
| Explicit | User supplied |
| Inherited | Parent policy |

### Generation Process

1. Identify eligible endpoints.
2. Generate permutations/combinations.
3. Apply endpoint filters.
4. Build topology signatures.
5. Apply safety caps.

Default maximum candidate count:

```text
1000
```

Output:

**Topology Candidate Registry**

---

## 5.4 Topology Candidate Registry

Immutable collection of generated topology signatures.

### Registry Fields

| Field | Description |
|--------|-------------|
| Solution | Domain + Solution |
| Generation Mode | Mode used |
| Endpoint Subset | Endpoints used |
| Signatures | Generated topology list |
| Total Count | Registry size |
| Timestamp | Generation time |
| Seed | Shuffle seed |

### Lifecycle

- Generated once per run
- Immutable
- Persisted
- Used by scheduler
- Used for coverage reporting

### Invariants

- Generated once
- Immutable
- Scheduler never modifies registry
- Scheduler stores only assignment state

### Optional Diagnostic Metadata

```json
{
  "signature": "postgres_to_mysql",
  "generated_from": {
    "template": "migration_v1",
    "endpoints": ["postgres", "mysql"],
    "generation_mode": "exhaustive"
  }
}
```

---

## 5.5 Topology Scheduler

Assigns topology signatures to tests.

### Scheduling Modes

| Mode | Description |
|------|-------------|
| Non-Repeating | Maximize diversity |
| Round-Robin | Circular assignment |
| Stable Minimal | Single topology |
| Preserve Prior | Reuse previous run |
| Benchmark Defined | Benchmark specific |
| Load Profile Defined | Load profile specific |

### Scheduling Algorithm

1. Accept registry and test list.
2. Compute deterministic seed.
3. Shuffle registry.
4. Create circular buffer.
5. Assign compatible topology.
6. Persist assignment state.

### Properties

- Solution scoped
- Deterministic
- Constraint aware
- Recoverable

### Scheduler Invariants

- Every assignment originates from registry.
- No duplicate assignment within an epoch when compatible unused topology exists.
- Deterministic assignment.
- Scheduler never creates topology signatures.
- Maximize unique assignments before reuse.

### Assignment State

| Field | Description |
|--------|-------------|
| Registry | Immutable registry reference |
| Unused | Remaining topologies |
| Used | Assigned topologies |
| Epoch | Current iteration |
| Pointer | Current registry position |
| Seed | Deterministic seed |

# 6. Depth Policies

| Policy | Generation | Scheduler | Repeat Strategy |
|---------|------------|-----------|-----------------|
| Sanity | Bounded | Stable Minimal | Allowed |
| Smoke | Representative | Round-Robin | Avoid Until Exhausted |
| Functional | Exhaustive | Non-Repeating | Avoid Until Exhausted |
| Regression | Inherited | Preserve Prior | Preserve |
| Performance | Explicit | Benchmark Defined | Benchmark |
| Load | Explicit | Load Profile Defined | Load Profile |

## 6.1 Performance and Load Limits

Performance and load pools must support explicit limits.

```yaml
performance:
  generation: explicit
  max_pool_size: 20

load:
  generation: explicit
  max_pool_size: 10
```

| Input | Behavior |

# 12. Acceptance Criteria

## 12.1 Discovery and Generation

- Integration endpoint catalog supports enable/disable.
- Templates define topology construction.
- Generator supports bounded, representative and exhaustive generation.
- Candidate pools are solution scoped.
- Registry stores endpoint subset.
- Registry remains immutable.
- Deterministic generation.
- Performance/load respect max pool size.
- Endpoint restriction filters generation.
- Explicit endpoints override policy caps.
- Optional diagnostic metadata supported.

---

## 12.2 Scheduling

- Multiple scheduling modes.
- Assignment state persisted.
- Constraint-aware assignment.
- Maximum topology diversity before reuse.
- No incompatible assignments.

---

## 12.3 CLI and Validation

- CLI uses `--topology-endpoints`.
- CLI supports domain, solution and endpoint filters.
- Resolution precedence implemented.
- Endpoint membership validation.
- Category compatibility validation.
- No infrastructure verification.
- Infrastructure failures occur during execution.
- Explicit endpoints override default caps.

---

## 12.4 Reporting

- Generated vs Assigned vs Executed metrics.
- Registry utilization reported.
- Per-signature statistics.
- Summary and detailed reports.
- Functional aggregation excludes topology.
- Coverage includes topology dimension.

---

## 12.5 Compatibility and Performance

- Backward compatible.
- Generic features bypass topology generation.
- Generation modes tested.
- Scheduling modes tested.
- Validated with 100+ integration endpoints.
