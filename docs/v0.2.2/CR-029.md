CR-029 — Dynamic Topology Generation & Scheduling Framework

Status

Approved for inclusion in RXTA v0.2.2

Type

Core Requirement (Architecture Enhancement)

---

1. Objective

Provide a topology generation and scheduling framework that automatically derives executable topology signatures from enabled integration endpoints and distributes them across validation workloads to maximize coverage while maintaining deterministic, bounded execution.

---

2. Problem Statement

Current topology selection in RXTA is static and manually declared. As integration endpoints expand beyond databases to include warehouses, object stores, streams, queues, REST APIs, and files, the combinatorial growth of valid topology combinations makes manual declaration unsustainable. Furthermore, executing every test against every topology creates unacceptable runtime explosion while providing diminishing validation returns.

Three core problems addressed:

1. Discovery — How are valid topologies identified from enabled endpoints?
2. Selection — How many and which topologies should be considered?
3. Assignment — Which topology should each test run on to maximize coverage?

---

4. Component Definitions

4.1 Integration Endpoints Catalog

A global registry of all available integration endpoints categorized by type:

· Databases — PostgreSQL, MySQL, MongoDB, Oracle, etc.
· Warehouses — Snowflake, BigQuery, Redshift, etc.
· Object Stores — S3, GCS, Azure Blob, MinIO, etc.
· Streams — Kafka, Pulsar, Kinesis, etc.
· Queues — SQS, RabbitMQ, ActiveMQ, etc.
· Search Engines — Elasticsearch, OpenSearch, Solr, etc.
· REST APIs — Various HTTP endpoints
· Files — File system, FTP, SFTP, etc.

Each endpoint includes:

· Enabled/disabled status
· Type classification
· Availability status
· Version metadata
· Capability flags (schema support, transactions, etc.)

Owned by: CR-024 (Catalog & Version Governance)
Consumed by: CR-029

4.2 Solution Topology Templates

Each solution defines how topologies are formed from integration endpoints:

Template Properties:

· Arity — Number of endpoints involved (2, 3, N)
· Ordering — Ordered (permutations) or Unordered (combinations)
· Slot Definitions — Which endpoint groups are eligible for each position
· Same-Endpoint Rules — Allow/disallow self-to-self or duplicate nodes
· Same-Type Rules — Allow/disallow same-type different instances
· Pattern — Naming template for signature strings

Example:

```
Solution: Migration
  Arity: 2
  Ordered: true
  Slot 1: databases, warehouses
  Slot 2: databases, warehouses
  Same-Endpoint: false
  Pattern: "{source}_to_{target}"
```

Owned by: CR-014 (Topology Planning)
Extends: CR-029 implementation

4.3 Topology Generator

Discovers all valid topology candidates from enabled endpoints:

Generation Modes:

· Bounded — Generate limited subset (sanity/smoke)
· Representative — Generate diverse sample
· Exhaustive — Generate all valid candidates
· Explicit — Use manually defined list
· Inherited — Use mode from parent policy

Generation Process:

1. Identify enabled endpoints matching slot requirements
2. Generate permutations (ordered) or combinations (unordered)
3. Apply same-endpoint and same-type filters
4. Format signatures using template pattern
5. Apply safety caps (default: 1000 candidates max)

Output: Topology Candidate Registry (solution-scoped)

---

4.4 Topology Candidate Registry (Immutable)

Solution-scoped collection of generated topology signatures:

Properties:

· Solution identifier
· Generation mode used
· List of signatures
· Total count
· Generation timestamp
· Seed used for shuffling

Lifecycle:

· Generated once per run per solution
· Immutable after generation
· Persisted in run metadata
· Used by scheduler for assignment
· Preserved for coverage reporting

Candidate Registry Invariants:

· Generated once per run.
· Immutable after generation.
· Scheduler never modifies registry.
· Scheduler only maintains assignment state.

---

4.5 Topology Scheduler

Assigns topologies to tests deterministically:

Scheduling Modes:

· Non-Repeating Best-Effort — Maximize diversity, avoid repeats until registry exhausted
· Round-Robin — Simple cycling through registry
· Stable Minimal — All tests use same topology
· Preserve Prior — Reuse topology from previous run
· Benchmark-Defined — Specific topology per performance test
· Load Profile-Defined — Topology per load scenario

Scheduling Algorithm:

1. Accept registry and test list
2. Seed = hash(run_id, solution_id, version)
3. Shuffle registry deterministically with seed
4. Treat registry as circular buffer with pointer and epoch
5. For each test:
   · Find next compatible topology (respecting constraints)
   · Mark as used/current
   · Advance pointer
   · If pointer reaches end, reshuffle (same seed + epoch) and reset
6. Record assignment metadata

Key Properties:

· Solution-scoped (each solution has independent scheduler state)
· Deterministic (same inputs → same assignments)
· Constraint-aware (respects test-specific requirements)
· Recoverable (assignment state persisted)

Scheduler Invariants:

· Every assigned topology shall originate from the generated candidate registry.
· No topology shall be assigned twice within an epoch while an unassigned compatible topology exists.
· Assignment shall remain deterministic for identical inputs.
· Scheduler shall never create new topology signatures.
· Scheduler shall maximize unique topology assignments before reuse whenever compatible candidates exist.

Assignment State:

· Registry (list of signatures) — immutable reference
· Unused (topologies not yet assigned in current epoch)
· Used (topologies assigned in current epoch)
· Epoch (iteration count)
· Pointer (current position)
· Seed (deterministic seed used)

4.6 Coverage Reporting

Metrics computed post-execution:

Topology Coverage:

· Generated count — Total candidates in registry
· Assigned count — Topologies assigned to tests by scheduler
· Executed count — Topologies that actually ran (assignments may be skipped)
· Coverage percentage — Executed / Generated × 100
· Unused topologies — Candidates never executed

Per-Signature Statistics:

· Topology signature
· Tests assigned
· Tests executed
· Pass / Fail / Skip counts
· Execution duration (optional)

Reporting Levels:

```
topology_reporting:
  summary: true                    # Default: compact report
  per_signature: true              # Detailed per-topology stats
  max_rows: 50                     # Limit for console output
  overflow: write_artifact         # Write full details to artifact
```

Default Report (Compact):

```
Functional: PASS
Regression: PASS
Performance: PASS
Load: PASS
```

Detailed Topology Coverage Stats (Separate Artifact):

```
Topology Coverage Stats
----------------------
Generated topologies : 80
Assigned topologies  : 32
Executed topologies  : 30
Coverage             : 37.5%
Skipped              : 2

Per-Signature Stats:
Topology Signature     Tests Assigned   Tests Executed   Pass   Fail   Skip
postgres_to_mysql      8                8                8      0      0
mysql_to_postgres      6                6                5      1      0
postgres_to_s3         4                3                3      0      1
...
```

Reporting Dimensions:

· By solution
· By generation mode
· By test category

Relationship to Existing Reports:

· Functional aggregation — Solution + Version (topology NOT included)
· Coverage Report — Includes topology metrics as separate dimension
· Benchmark Report — May include topology as dimension

9. Acceptance Criteria

· Integration endpoints catalog supports enable/disable by category
· Solution topology templates define arity, ordering, and slot requirements
· Topology generator produces bounded, representative, and exhaustive candidate pools
· Candidate pools are solution-scoped
· Candidate registry is immutable after generation
· Deterministic shuffling uses hash(run_id, solution_id, version)
· Topology scheduler supports multiple assignment modes
· Assignment state is persisted for recovery
· Constraint-aware assignment respects test requirements
· Scheduler maximizes unique topology assignments before reuse
· Coverage metrics report generated vs assigned vs executed topologies
· Per-signature statistics include tests assigned, executed, pass, fail, skip
· Reporting supports summary and detailed levels
· Functional aggregation excludes topology dimension
· Coverage report includes topology as separate dimension
· Generated topology signatures are deterministic for identical inputs
· Topology scheduler never assigns an incompatible topology to a test
· Full backward compatibility with manually defined topologies
· Tests cover all generation modes
· Tests cover all scheduling modes
· Performance validated with 100+ integration endpoints

---

10. Benefits

· Scalability — Handles 5 to 500 integration endpoints without explosion
· Coverage — Exhaustive discovery ensures no topology overlooked
· Efficiency — Non-repeating assignment maximizes diversity per test
· Determinism — Reproducible scheduling enables debugging
· Separation of Concerns — Generation and scheduling independently configurable
· Reporting — Topology coverage becomes measurable governance metric
· Evolution — New integration endpoints automatically included in topology discovery
· Visibility — Per-signature statistics enable targeted topology debugging

---

11. Final Notes

This CR provides the missing topology orchestration layer in RXTA. It cleanly separates discovery (generation) from execution planning (scheduling), maintains determinism for reproducibility, and introduces measurable coverage metrics without polluting functional pass/fail aggregation.

The architecture is generic enough to support future scheduling dimensions (database version, cloud region, worker core) without structural changes to the scheduler itself.
