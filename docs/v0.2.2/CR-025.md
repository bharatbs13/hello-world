# CR-025 — Execution Profile Framework

## Status

Proposed

## Target Version

v0.2.2

---

# 1. Problem Statement

RXTA currently uses phase-oriented execution concepts:

- phase1
- phase2

The phase model originated from the initial UAT implementation and was primarily used to distinguish mock-based validation from real infrastructure validation.

As RXTA evolved, phase became an implementation detail rather than a meaningful execution control mechanism.

The framework now requires explicit control over execution environments while preserving:

- Suite selection
- Regression governance
- Topology expansion
- Benchmark execution

The current phase model does not clearly express:

- Pure registry/configuration validation
- Mock connector validation
- Real infrastructure validation

and does not provide a clean execution-selection contract for users.

---

# 2. Objective

Introduce an execution-profile-based execution model.

Execution profile becomes the authoritative environment eligibility mechanism for UAT execution.

Phase remains a legacy filesystem concept and is no longer used for execution selection.

---

# 3. Execution Model

RXTA execution selection shall be governed by three orthogonal dimensions:

```text
coverage_tier
      ×
validation_type
      ×
execution_profile
````

---

## 3.1 Coverage Tier

Controls execution breadth.

Supported values:

* smoke
* sanity
* feature

CLI alias:

```text
full → feature
```

---

## 3.2 Validation Type

Controls test origin.

Supported values:

* current
* regression
* all

Definitions:

### current

* Current PV tests only

### regression

* Promoted regression tests only

### all

* Current and regression tests

---

## 3.3 Execution Profile

Controls environment eligibility.

## Catalog-supported values

* no_db
* mock_db
* real_db

## CLI-supported values

* mock_db
* real_db
* all_db

Optional:

* no_db (debug/advanced use)

---

# 4. Catalog Contract

Each UAT test case shall declare:

```yaml
execution_profiles:
  - no_db
```

or

```yaml
execution_profiles:
  - mock_db
```

or

```yaml
execution_profiles:
  - real_db
```

Multiple profiles are permitted.

Example:

```yaml
execution_profiles:
  - mock_db
  - real_db
```

---

# 5. Execution Profile Expansion

CLI selectors shall expand as follows:

| CLI Selector | Expansion                 |
| ------------ | ------------------------- |
| mock_db      | no_db + mock_db           |
| real_db      | real_db                   |
| all_db       | no_db + mock_db + real_db |

`all_db` shall not be stored in catalogs.

---

# 6. Execution Resolution Order

Execution shall be resolved using:

```text
coverage_tier
        ↓
validation_type
        ↓
execution_profile
        ↓
topology expansion
        ↓
execution matrix
```

---

# 7. Backward Compatibility

Existing catalog field:

```yaml
phases:
```

may remain for compatibility and traceability.

Execution selection shall not depend on phase membership.

Phase becomes informational only.

---

# 8. Directory Structure

v0.2.2 shall retain:

```text
phase1/
phase2/
```

directory names.

Directory naming is not authoritative.

Execution profile metadata is authoritative.

Future versions may rename directories without affecting execution semantics.

---

# 9. CLI Contract

Examples:

```bash
rxta test --coverage-tier smoke
```

```bash
rxta test --coverage-tier full
```

```bash
rxta test \
  --coverage-tier full \
  --validation-type regression
```

```bash
rxta test \
  --coverage-tier full \
  --execution-profile all_db
```

---

# 10. Non-Goals

This CR does not:

* Rename directories
* Modify topology planning
* Modify regression governance
* Modify benchmark execution
* Modify report aggregation

Those concerns remain owned by their existing CRs.
