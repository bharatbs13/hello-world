# CR-028 — Best-Effort Backend Provisioning and Runtime Eligibility

Status

Approved for v0.2.2

---

Objective

Define how RXTA handles multi-backend UAT when backend installation/setup is best-effort and only a subset of supported backends becomes available.

RXTA shall run UAT only against backends that are both:

```text
RXTA-supported
AND
successfully installed
AND
successfully setup
AND
verified ready
```

---

Problem

RXTA may support multiple storage backends, for example:

```text
postgres
mysql
mariadb
sqlite
duckdb
clickhouse
mongodb
```

However, during environment provisioning, some backends may fail installation, fail setup, or fail readiness verification.

RXTA must not assume happy-path installation.

---

Required Behaviour

Backend provisioning shall be best-effort.

If one backend fails, RXTA shall continue attempting remaining backends.

At least one real database backend must be successfully installed, setup, and verified for UAT execution to proceed.

If no real backend is ready, UAT shall not start.

---

Orchestration Layer

RXTA shall provide a single provisioning orchestrator that maintains runtime state across lifecycle phases.

```text
relix-deploy provision-storage --all
```

Internally, the orchestrator shall:

1. Call install_storage.sh --all
2. Record installation outcomes per backend
3. Call setup_uat_storage.sh only for backends with INSTALL_SUCCESS
4. Record setup outcomes per backend
5. Call verify_storage.sh --all
6. Compute eligibility based on all three phases
7. Print a high-visibility eligibility summary
8. Return an overall exit status

The orchestrator shall not merge the separate lifecycle scripts. Each script retains its distinct safety profile and governance as defined in CR-026:

Script Safety Profile
install_storage.sh Can change OS packages
setup_uat_storage.sh Can create DB/users/schema
verify_storage.sh Must be read-only
cleanup_storage.sh Can destroy/reset UAT state

---

Backend Provisioning State Machine

RXTA shall maintain a state machine for each backend during provisioning.

State transitions:

```text
                    ┌──────────────┐
                    │  SUPPORTED   │
                    └──────┬───────┘
                           │ install
                           ▼
                    ┌──────────────┐
                    │    INSTALL   │
                    │──────────────│
                    │ NOT_STARTED  │
                    │ SUCCESS      │
                    │ FAILED       │
                    │ SKIPPED      │
                    └──────┬───────┘
                           │ setup (only if INSTALL = SUCCESS)
                           ▼
                    ┌──────────────┐
                    │     SETUP    │
                    │──────────────│
                    │ NOT_STARTED  │
                    │ SUCCESS      │
                    │ FAILED       │
                    │ SKIPPED      │
                    └──────┬───────┘
                           │ verify
                           ▼
                    ┌──────────────┐
                    │    VERIFY    │
                    │──────────────│
                    │ NOT_STARTED  │
                    │ READY        │
                    │ NOT_READY    │
                    │ SKIPPED      │
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │   ELIGIBLE   │
                    │──────────────│
                    │ YES          │
                    │ NO           │
                    └──────────────┘
```

Each backend shall track:

Field Values
supported true, false
install_status NOT_STARTED, SUCCESS, FAILED, SKIPPED
setup_status NOT_STARTED, SUCCESS, FAILED, SKIPPED
verify_status NOT_STARTED, READY, NOT_READY, SKIPPED
eligible true, false
diagnostic_reason String

---

Eligibility Rule

A backend is UAT-eligible only when:

```text
supported == true
install_status == SUCCESS
setup_status == SUCCESS
verify_status == READY
eligible == true
```

Backends that fail any required stage are marked eligible = false and removed from the active UAT backend list.

---

Visibility Requirement

RXTA shall print a high-visibility summary after provisioning:

```text
Supported backends:
  postgres mysql mariadb sqlite duckdb clickhouse mongodb

Successfully provisioned:
  postgres sqlite duckdb

Excluded from UAT:
  mysql       INSTALL_FAILED
  mariadb     SETUP_FAILED
  clickhouse  VERIFY_NOT_READY
  mongodb     NOT_INSTALLED

Final UAT backend set:
  postgres sqlite duckdb
```

---

Manual Governance

Operators are responsible for ensuring that the intended supported backend list and the actually installed backend list match when full coverage is required.

RXTA shall make mismatches visible but shall not silently treat unavailable backends as tested.

---

UAT Selection Rule

UAT shall run only on:

```text
supported_backends ∩ successfully_provisioned_backends ∩ verified_ready_backends
```

Any skipped or failed backend shall be excluded from execution and reported clearly.

---

Minimum Readiness Gate

UAT may proceed only if:

```text
eligible_real_backend_count >= 1
```

If the eligible backend count is zero:

```text
Overall backend readiness: NOT_READY
UAT execution: BLOCKED
```

---

Automated Workflow

For v0.2.2, CR-026 and CR-028 shall make provisioning automated through:

```bash
relix-deploy provision-storage --all
relix-deploy verify-storage --all
```

---

Acceptance Criteria

· RXTA does not assume all supported backends installed successfully.
· Install/setup/verify continues best-effort across backends.
· Backend provisioning state machine tracks state per backend.
· Failed backends are excluded from UAT execution.
· At least one real backend must be ready before UAT starts.
· Final active backend list is printed clearly.
· Unsupported, failed, skipped, and not-ready backends include diagnostic reasons.
· UAT reports distinguish between supported backends and actually tested backends.
· Separate lifecycle scripts (install_storage.sh, setup_uat_storage.sh, verify_storage.sh, cleanup_storage.sh) are preserved with distinct safety profiles as defined in CR-026.
· A provisioning orchestrator (relix-deploy provision-storage) coordinates the scripts and maintains state machine.
· Automated workflow is specified for v0.2.2.
